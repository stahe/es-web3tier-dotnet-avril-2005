    2.2. La aplicación webarticles: reseña

    A continuación presentamos los componentes de la aplicación web de comercio electrónico simplificada que se describió en la primera parte. Esta aplicación permite a los usuarios de la web:

    • ver una lista de artículos de una base de datos
    • añadir algunos de ellos a un carrito de la compra electrónico
    • confirmar el carrito. Esta confirmación simplemente actualiza los niveles de inventario de los artículos comprados en la base de datos.

    2.2.2. Arquitectura general de la aplicación

    La aplicación creada en la Parte 1 tiene una arquitectura de tres capas:

    • Las tres capas se han hecho independientes mediante el uso de interfaces
    • La integración de las diferentes capas se ha implementado utilizando Spring
    • Cada capa tiene su propio espacio de nombres: web (capa de interfaz de usuario), domain (capa de negocio) y dao (capa de acceso a datos).

    La aplicación sigue una arquitectura MVC (Modelo-Vista-Controlador). Si nos remitimos al diagrama de capas anterior, la arquitectura MVC encaja en él de la siguiente manera:

    El procesamiento de una solicitud del cliente sigue estos pasos:

    1. El cliente envía una solicitud al controlador. Este controlador es, en este caso, una página .aspx que desempeña una función específica. Se encarga de gestionar todas las solicitudes de los clientes. Es el punto de entrada de la aplicación. Es la C de MVC.
    2. El controlador procesa esta solicitud. Para ello, puede necesitar la ayuda de la capa de negocio, conocida como la M en la estructura MVC.
    3. El controlador recibe una respuesta de la capa de negocio. La solicitud del cliente ha sido procesada. Esto puede dar lugar a varias respuestas posibles. Un ejemplo clásico es
      • una página de error si la solicitud no se ha podido procesar correctamente
      • una página de confirmación en caso contrario
    4. El controlador elige la respuesta (= vista) que se enviará al cliente. Suele tratarse de una página que contiene elementos dinámicos. El controlador proporciona estos elementos a la vista.
    5. La vista se envía al cliente. Esta es la V de MVC.

    2.2.5. Revisión de la capa [DAO]

    En nuestra primera implementación de la capa [dao], la interfaz de acceso a datos [IArticlesDao] se implementó mediante una clase que almacenaba los elementos en un objeto [ArrayList]. Esto nos permitió evitar complicar en exceso esta capa y demostrar que solo importaba su interfaz, no su implementación. Así, pudimos crear una aplicación web funcional. Esta aplicación tiene tres capas: [web], [domain] y [dao]. Aquí propondremos diferentes implementaciones de la capa [dao]. Cada una de ellas puede sustituir a la capa [dao] actual sin necesidad de modificar las capas [domain] y [web]. Esta flexibilidad se consigue porque:

    • la capa [domain] no hace referencia a una clase concreta, sino a una interfaz [IArticlesDao]
    • gracias a Spring, pudimos ocultar el nombre de la clase que implementa la interfaz [IArticlesDao] a la capa [domain].

    2.3. La clase de implementación [ArticlesDaoPlainODBC]

    Proponemos una nueva implementación de la capa [dao] que asume que los datos se encuentran en una fuente ODBC.     2.5.6.1. El producto Ibatis SqlMap

    Hemos escrito cuatro implementaciones diferentes de la capa [dao] para nuestra aplicación [webarticles]. En cada caso, pudimos integrar la nueva capa [dao] en la aplicación [webarticles] sin necesidad de recompilar las otras dos capas, [web] y [domain]. Esto se logró, como recordatorio, mediante dos decisiones arquitectónicas:

    • acceso a las capas a través de interfaces
    • integración de las capas utilizando Spring

    Queremos ir un paso más allá. Aunque son diferentes, nuestras cuatro implementaciones de la capa [dao] comparten similitudes sorprendentes. Una vez escrita la primera implementación, las otras tres se crearon casi en su totalidad copiando y pegando y sustituyendo ciertas palabras clave por otras. La lógica, sin embargo, se mantuvo sin cambios. Uno podría preguntarse si sería posible tener una única implementación que nos liberara de los diversos métodos de acceso a los datos. Hemos utilizado cuatro:

    • acceso a través de un controlador ODBC a una fuente de datos ODBC
    • acceso directo a una base de datos SQL Server
    • acceso a través de un controlador Ole DB a un origen de datos Ole DB
    • acceso directo a una base de datos Firebird

    La herramienta Ibatis SqlMap [[http://www.ibatis.com/]] permite desarrollar capas de acceso a datos independientes de la naturaleza concreta de la fuente de datos. El acceso a los datos se realiza a través de:

    • archivos de configuración que contienen información que define la fuente de datos y las operaciones que se van a realizar en ella
    • una biblioteca de clases que utiliza esta información para acceder a los datos

    La herramienta Ibatis SqlMap se desarrolló inicialmente para la plataforma Java. Su adaptación a la plataforma .NET es reciente y parece presentar algunos errores (opinión personal que requeriría una verificación exhaustiva). No obstante, dado que la herramienta ha demostrado su eficacia en la plataforma Java, parece que merece la pena presentar la versión .NET.

    2.5.6.3. Archivos de configuración de iBatis SqlMap

    Se definirá una fuente de datos [SqlMap] utilizando los siguientes archivos de configuración:

    1. providers.config: define las bibliotecas de clases que se utilizarán para acceder a los datos
    2. sqlmap.config: define los parámetros de conexión
    3. Archivos de mapeo: definen las operaciones que se realizarán sobre los datos

    La lógica detrás de estos archivos es la siguiente:

    • Para acceder a los datos, necesitaremos una conexión. Para representarla, ya hemos visto varias clases: OdbcConnection, SqlConnection, OleDbConnection, FbConnection. También necesitaremos un objeto [Command] para ejecutar consultas SQL: OdbcCommand, SqlCommand, OleDbCommand, FbCommand, etc. En el archivo [providers.config], definimos todas las clases que necesitamos.
    • El archivo [sqlmap.config] define esencialmente la cadena de conexión a la base de datos que contiene los datos. La conexión a la base de datos se abrirá instanciando la clase [Connection] definida en [providers.config], a cuyo constructor se le pasará la cadena de conexión definida en [sqlmap.config].
    • Los archivos de mapeo definen:
      • las asociaciones entre las filas de las tablas de datos y las clases .NET, cuyas instancias contendrán dichas filas
      • las operaciones SQL que se deben ejecutar. Estas se identifican mediante un nombre. El código .NET ejecuta estas operaciones a través de sus nombres, lo que elimina todo el código SQL del código .NET.

    2.5.6.5. La API de SqlMap

    Las clases de SqlMap se encuentran en DLL que suelen ubicarse en la carpeta [bin] de la aplicación:

    Las aplicaciones que utilicen clases SqlMap deben importar el espacio de nombres [IBatisNet.DataMapper]:

    Imports IBatisNet.DataMapper

    Todas las operaciones SQL se realizan a través de un singleton de tipo [Mapper], una clase del espacio de nombres [IBatisNet.DataMapper]. El singleton se obtiene de la siguiente manera:

            Dim mappeur As SqlMapper = Mapper.Instance

    Para ejecutar el comando SqlMap [getAllArticles], escribimos:

                        dim articles as IList=mappeur.QueryForList("getAllArticles", Nothing)
    • El método [QueryForList] devuelve el resultado de un comando SELECT como una lista
    • El primer parámetro es el nombre del comando SQL que se va a ejecutar (véase articles.xml)
    • El segundo parámetro es el parámetro que se va a pasar a la consulta SQL. Debe corresponder al atributo [parameterClass] del comando SqlMap. En [articles.xml], tenemos [parameterClass=Nothing]. Por lo tanto, aquí pasamos un puntero nulo.
    • El resultado es de tipo IList. Los objetos de esta lista se especifican mediante el atributo [resultMap] del comando SQL-select: [resultMap="article"]. «article» es un nombre de mapeo: 
    <resultMap id="article" class="istia.st.articles.dao.Article">

    La clase asociada a esta asignación es [istia.st.articles.dao.Article]. En definitiva, la variable [articles] definida anteriormente es una lista de objetos [istia.st.articles.dao.Article]. Así, con esta nueva capa, pudimos utilizar sucesivamente las fuentes de datos de las implementaciones anteriores 1 a 3. Esto se hizo de forma transparente mediante archivos de configuración.
    • Demostramos la gran flexibilidad que las herramientas Spring y SqlMap aportan a las aplicaciones web de tres capas.
